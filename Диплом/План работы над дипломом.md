# Разработка программной системы анализа сетевой связности и формирования сетевых политик в Kubernetes

## Описание темы
Предположим есть развернутый k8s с микросервисами. Можно обратиться к API k8s и извлечь данные о связности объектов(микросервисов или подов). 
1) Извлекли из api информацию о доступности (граф разрешенной связности, те взаимодействия которые мы прописали в конфигах кубера).
2) Берем данные трейсинга (информация о пути прохождения запроса через микросервисы и компоненты кластера) для этого существуют библиотеки (например OpenTelemetry - сбор телеметрии в k8s). Суть в том что мы даём нагрузку и смотрим куда реально ходит трафик. Получаем граф связности сущностей по нашим наблюдениям. Какие то взаимодействия могут происходить вне описания. А какие то наоборот не происходить.
3) Граф требуемой связности (это граф взаимодействий который описывается в документации(схема сетевой связности, архитектура информационной системы)). Этот граф плод творения архитектора.
`Эти графы могут не совпадать!`
При этом можно поставить граф сетевой связности, опираясь на граф требуемый связности, который описан в документе.
Граф требуемой связности так или иначе придётся написать.

В сумме есть 3 графа:
1) Граф разрешенной связности
2) Граф наблюдаемой связности 
3) Граф требуемой связности
Нормальное состояние это когда взаимодействие присутствует во всех 3-х графах.
* Если взаимодействие присутствует в требуемом, разрешенном графе, но нет в наблюдаемом > значит это взаимодействие не состоялось либо у нас устаревшая документация и это взаимодействие не используется в реальности.
* Если взаимодействие есть в требуемом графе, но нет в разрешенном и наблюдаемом графе > ошибка настройки манифеста.
* Если взаимодействия нет в требуемом и наблюдаемом графе, но есть в разрешенном > избыточная настройка. 
* Если взаимодействия нет в требуемом, но есть в разрешенном и есть в наблюдаемом > незадокументированное взаимодействие.
* Если взаимодействия нет в требуемом и нет в разрешенном но есть в наблюдаемом > ошибка настройки (требует доп. изучений).

При возникновении аварии команда на проде может изменить конфигурацию и соответственно граф. 
## Проблемы
* Необходимо обозначить что является вершиной графа (нода, под, микросервис)
* Насколько сложным будут сетевые взаимодействия (они могут быть например с service meshами)
* Придумать правила, по которым программа будет анализировать графы.
## Ожидаемый результат
* Стенд с микросервисами.
* Приложение которое будет содержать скрипты собирающие конфигурацию из k8s API.
* Приложение будет анализировать графы, по правилам (которые мне нужно придумать) и выдавать рекомендации. 
* Микросервисы будут просто генераторами трафика. 
* Для усиления диплома собрать кубер с доплнительными компонентами (они будут влиять на собираемый граф).
